# 0003. Внешние интеграции — отдельные бандлы, доступ из приложения только через клиент-обёртку в `Core\Client`

**Статус:** ✅ Принято \
**Дата:** 2026-09-27

> Решение о бандлах и клиентах-обёртках действовало в коде и раньше, но нигде не было зафиксировано, кроме описания текущего устройства в `CLAUDE.md`. Этот ADR оформляет его задним числом и добавляет правило для исключений, найденное в [`../features/2026-09-08-minor-findings.md`](../features/2026-09-08-minor-findings.md).

## Контекст

Школе нужны внешние интеграции: эквайринг (выставление счетов и проверка оплаты), ОФД (фискальные чеки), отправка уведомлений. Настоящих интеграций пока нет, их имитируют заглушки. Позже их заменят реальными API, и эта замена не должна задевать бизнес-логику `Billing`/`Person`.

Интеграции оформлены как самостоятельные Symfony-бандлы вне `App\`: `AcquiringBundle`, `FiscalDataOperatorBundle`, `NotifierBundle`, у каждого свой PSR-4-неймспейс и свой `services.yaml`. Синхронные интеграции (эквайринг, ОФД) открывают наружу один `Facade`, а приложение вызывает его через обёртку `App\Core\Client\<Integration>\<Integration>Client`. Клиент переводит DTO ядра в DTO бандла.

При ревью 2026-09-27 выяснилось, что правило соблюдается только для DTO. `AcquiringClient` и `FiscalDataOperatorClient` пропускали наружу исключения бандлов (`AcquiringException`, `FiscalDataOperatorException`), поэтому юзкейсы `Billing` неявно зависели от классов бандлов. Правило было записано только как описание устройства, а не как решение с обоснованием, и его соблюдали «по памяти»: для DTO помнили, для исключений забыли.

## Решение

1. **Каждая внешняя интеграция — отдельный бандл** вне `App\`. Он регистрирует свои сервисы сам и не импортирует бизнес-контексты (`App\Billing`, `App\Person`). Бандлу разрешено зависеть от инфраструктуры `App\Core`: `UnitOfWorkInterface`, `EntityIdGeneratorInterface`, `Ampq`, трейты Doctrine. Это общее ядро, а не бизнес-логика.
2. **Синхронная интеграция открывает один `Facade`**, это единственная публичная точка входа в бандл.
3. **Приложение обращается к фасаду только через клиент** `App\Core\Client\<Integration>\<Integration>Client` (`final readonly`). Юзкейсы `Billing`/`Person` зависят только от `Core\Client\*`. Клиент — это Anti-Corruption Layer на границе с интеграцией. Всё, что пересекает эту границу, переводится:
   - **входные и выходные данные**: DTO ядра (`Core\Client\<Integration>\*Dto`) ↔ DTO бандла. Скаляры и стандартные типы PHP (`string`, `DateTimeImmutable`) передаются как есть;
   - **исключения**: клиент ловит любое исключение из вызова фасада (`Throwable`, а не только собственные исключения бандла — фасад может уронить и инфраструктура, например `flush()`) и выбрасывает своё (`Core\Client\<Integration>\<Integration>ClientException`), а исходное кладёт в `previous`. Конструктор исключения клиента принимает только сообщение и `previous`, без кода: коды исходных исключений разнородны (у `PDOException` это строка SQLSTATE), и копировать их в обёртку бессмысленно — код исходного доступен через `getPrevious()`. Метод клиента объявляет исключение в `@throws`.
4. **Асинхронная интеграция (`NotifierBundle`)** не имеет фасада и клиента. Приложение отправляет команду `App\Core\Ampq\Event\NotifyPersonCommand` через `MessageBus`, её обрабатывает консюмер внутри бандла. Здесь граница — это само сообщение в `Core\Ampq\Event`, поэтому оно не должно ссылаться на типы бандла (см. «Последствия», известное отступление).

## Последствия

**Плюсы:**
- Заглушку можно заменить реальным API, не трогая юзкейсы: меняются бандл и, при необходимости, клиент.
- Юзкейсы обрабатывают ошибки интеграции по типу ядра, не зная, какой бандл их выбросил. Исходная причина не теряется, она доступна через `getPrevious()`.
- Клиент — единственное место, где приложение знает о бандле. Поэтому его удобно проверять Unit-тестами (`tests/Unit/Core/Client/*`) на настоящей заглушке фасада, без моков.

**Минусы / цена:**
- На каждую интеграцию приходится минимум три класса ядра (клиент, DTO, исключение) при тонком фасаде. Для заглушек это заметная доля кода.
- Клиент ловит `Throwable`, поэтому ошибка программиста (`TypeError`, `ArgumentCountError` в клиенте или фасаде) выглядит для приложения как «ошибка эквайринга/ОФД». Исходная причина сохраняется в `getPrevious()`.
- Сейчас правило соблюдается только соглашением. Автоматической проверки нет, её можно добавить инструментом анализа зависимостей (см. [`../features/2026-09-27-person-billing-acl-level-3.md`](../features/2026-09-27-person-billing-acl-level-3.md), deptrac).
- **Известное отступление (на 2026-09-27):** `NotifyPersonCommand` в `Core\Ampq\Event` и `Billing\Presentation\Amqp\Consumer\ContractCreated\Handler` импортируют `NotifierBundle\Enum\PersonTypeEnum`. Ядро и `Billing` зависят от типа бандла, а это нарушает п. 4. Исправить можно так: завести свой enum (или скаляр) в `Core` и переводить его в консюмере бандла. В этом ADR не исправлено.

## Отклонённые варианты

- **Юзкейсы вызывают фасад бандла напрямую, без клиента.** Меньше классов, но юзкейсы начинают зависеть от DTO и исключений бандла, и замена интеграции задевает бизнес-логику. Отклонено: изоляция бизнес-логики от интеграции — главная причина, по которой бандлы вообще выделены.
- **Клиент переводит DTO, а исключения бандла пропускает наружу** (так было до этого ADR). Вызывающий код ловит `Throwable`, поэтому явного импорта не видно, но от бандла зависит сам смысл ошибки: при замене бандла меняется тип и текст исключения, которое видит приложение. К тому же точечно обработать ошибку интеграции можно только по классу бандла. Отклонено: такая граница изолирует только наполовину.
- **Общее исключение `IntegrationException` для всех клиентов.** Меньше классов, но юзкейс, работающий с несколькими интеграциями (например, `CheckInvoicesPaidUseCase`: эквайринг и ОФД), не сможет различить, какая из них упала. Отклонено в пользу отдельного исключения на каждого клиента. Общего родителя можно ввести позже, если он понадобится.
