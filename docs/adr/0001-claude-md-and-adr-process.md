# 0001. Вести `CLAUDE.md` и Architecture Decision Records в репозитории

**Статус:** ✅ Принято \
**Дата:** 2026-09-08

## Контекст

Проект ведётся с активным участием AI-ассистента (Claude Code) в разных сессиях — сессии не разделяют память между собой, каждая начинается «с нуля» и восстанавливает контекст только из репозитория (код, `git log`, `CLAUDE.md`).

В репозитории уже есть `CLAUDE.md` (добавлен в `6b1a800`) — гид по текущему состоянию проекта: структура, границы модулей, команды, стиль кода. Он хорошо решает задачу «быстро ввести в курс дела», но не предназначен хранить историю: почему решение принято именно так, какие варианты отклонили и почему. Если начать дописывать в него ещё и рационале — файл раздувается и быстро расходится с кодом (у него нет версии «протухло», как у решения).

## Решение

1. `CLAUDE.md` остаётся гидом по **текущему состоянию** — структура, команды, конвенции. Никакой истории решений и рационале туда не добавляем, только то, что верно прямо сейчас.
2. Заводим `docs/adr/` — лёгкие Architecture Decision Records, один файл — одно решение. Правила (когда писать, формат, статусы, нумерация) — в `docs/adr/README.md`, шаблон — в `docs/adr/template.md`.
3. `CLAUDE.md` получает короткую отсылку к `docs/adr/`, чтобы любая сессия (ассистента или разработчика) проверяла существующие записи до пересмотра архитектурных вопросов.
4. Нумерация начинается с этой записи (`0001`) — по классике формата ADR первая запись фиксирует сам факт ведения ADR.

## Последствия

**Плюсы:**
- Архитектурные решения переживают отдельную сессию/чат — не нужно заново находить и переспоривать то, что уже решено.
- `CLAUDE.md` остаётся компактным и не протухает — в нём нет исторического балласта.
- Явное место для фиксации отклонённых вариантов — самая ценная и самая теряемая часть любого обсуждения.

**Минусы / цена:**
- Дополнительная дисциплина: значимое решение теперь требует файла, а не только кода/коммита.
- Ещё один документ, за актуальностью статусов которого нужно следить (митигируется правилом «не редактировать задним числом» — см. `README.md`).

## Отклонённые варианты

- **Полагаться на `git log`/commit-сообщения** — история изменений есть, но без структуры и без явного раздела «что рассматривали и отклонили»; найти причину конкретного архитектурного выбора среди сотен коммитов дорого.
- **Писать рационале прямо в `CLAUDE.md`** — самый простой вариант, но именно он приводит к разрастанию файла, который должен оставаться быстрым для чтения; при изменении решения пришлось бы задним числом переписывать историю, а не добавлять новую запись.
- **Не формализовать процесс, полагаться на память чата** — то, что уже не сработало: в рамках этой же сессии решение по `Person`/`Billing` едва не было переспорено заново на следующем шаге, потому что аргументация нигде не была явно зафиксирована.
