# Feature Logs

Один файл — одна задача/фича (любого размера, от однострочного фикса до многодневного рефакторинга): статус, цель, план, что сделали, что не стали. Не журнал коммитов и не архитектурное решение — рабочий дневник конкретной задачи, чтобы через день/неделю (или в новой сессии с ассистентом) не восстанавливать контекст заново по чату или по `git log`.

## Чем это отличается от ADR и от commit/PR

- **[ADR](../adr/README.md)** (`docs/adr/`) — архитектурные решения: границы модулей, выбор технологии, сознательно отклонённые варианты с весомыми последствиями. Живёт отдельно от конкретной фичи и может пережить её.
- **`docs/features/`** — операционная сторона одной фичи: что сделали, что не стали, в каком порядке, как менялся план по ходу работы. Если в процессе принято архитектурное решение — **не пересказывать его здесь, а оформить ADR и сослаться** (пример: [`2026-09-08-refactoring-plan.md`](2026-09-08-refactoring-plan.md) → [ADR-0002](../adr/0002-person-billing-acl.md), решение по изоляции `Person`/`Billing` описано один раз, в ADR).
- **Commit-сообщение / PR** — единица правды по конкретному дифу, всегда точнее всего про «что именно поменялось». Feature-файл не заменяет их, а даёт более высокий уровень: зачем и что в целом, не построчно.

## Когда писать

Пишем всегда — любое изменение проекта, от однострочного фикса до многодневной фичи, получает свой файл. Глубина заполнения при этом пропорциональна масштабу: для точечного фикса «Сделано» может быть одной строкой, а «Не стали делать» — пустым, не нужно высасывать содержимое из пальца ради полноты шаблона.

Файл создаётся **в момент начала планирования**, не постфактум: план идёт в файл сразу, а не пишется задним числом после того, как всё уже сделано. По ходу работы разделы «Сделано» / «Не стали делать» дополняются вживую, черновые формулировки на этом этапе — норма. Обязательный проход «убрать лишнее, оставить суть» делается **при смене статуса** на ✅/⏸️/❌ — не когда-нибудь потом, а в тот момент, когда статус меняется. Без этой привязки черновик так и останется черновиком навсегда.

Если по ходу работы напрашивается архитектурное решение (граница модулей, выбор технологии, отклонённый вариант с весомыми аргументами — см. [`../adr/README.md`](../adr/README.md), «Когда писать ADR») — не описывать его в feature-файле, предложить оформить отдельным ADR и сослаться.

## Формат

Шаблон — [`template.md`](template.md).

- **Имя файла**: `YYYY-MM-DD-название-фичи.md` — дата **создания** файла, имя — по смыслу фичи (задачи), не по имени ветки и не по календарной сессии чата. Ветки переименовываются в процессе работы (так уже случилось в этом проекте: `fix/person-billing-kernel` → `feature/acl-refactoring-person-billing`), а одна сессия чата может касаться нескольких разных фич или растягиваться на много сессий за много дней — ни то, ни другое не годится как единица группировки, годится только сама фича/задача.
- Несколько фич в один день — это не коллизия, у них естественно разные слаги в названии. Если слаг случайно совпал — добавить `-2`, `-3`.
- Индекс ниже обновляется при добавлении **каждого** нового файла — это часть создания записи, а не отдельная задача на потом.
- **Секции**: Статус / Начато / Обновлено, Цель, План, Сделано, Не стали делать, Изменённые файлы, Ссылки — см. шаблон.
- **Статусы**:
  - 🟡 **В работе** — фича ещё не готова.
  - ✅ **Готово** — сделано и смёржено.
  - ⏸️ **Приостановлено** — работа стоит, но не отменена.
  - ❌ **Отменено** — решили не делать.
- Поле **«Обновлено»** обязательно и живёт отдельно от даты в имени файла — иначе старая по имени фича выглядит закрытой, даже если работа над ней продолжается.
- Раздел **«Изменённые файлы»** — не вести построчно вручную, это гарантированно разойдётся с кодом. Вставить `git diff --stat <база>...<ветка>` (или ссылку на PR) один раз перед завершением/мёржем, как снимок на момент готовности, а не поддерживать всю жизнь фичи.
- Архитектурные решения внутри фичи — не пересказывать, оформлять отдельным ADR и ссылаться (см. [`docs/adr/README.md`](../adr/README.md), раздел «Когда писать ADR»).
