# Рабочий дневник изменений проекта (docs/features)

**Статус:** 🟡 В работе \
**Начато:** 2026-09-16 \
**Обновлено:** 2026-09-17

## Цель

После ADR (`docs/adr/`, заведён раньше) не хватало более лёгкого места для фиксации хода конкретной задачи — не архитектурного решения, а «что делаем, зачем, что уже сделали, что решили не делать». Без этого контекст задачи жил только в чате и терялся между сессиями ассистента (в частности, ACL-рефакторинг `Person`↔`Billing` чуть не пришлось пересматривать заново на ровном месте). Цель — завести `docs/features/` как рабочий дневник фичи/ветки, с чёткой границей: где кончается ADR и начинается дневник, чтобы не дублировать одно и то же в двух местах.

## План

1. Обсудить идею (челлендж): какие риски у отдельной папки под дневники фич, сравнить с ADR и с commit/PR.
2. Сформулировать разделение ответственности: ADR — «почему архитектурно так», `docs/features` — «что и зачем в рамках задачи», commit/PR — «что именно в дифе».
3. Создать `docs/features/README.md` (правила) и `template.md` (шаблон).
4. Обновить `CLAUDE.md` — добавить ссылки на оба места с разницей в одну строку.
5. Завести первый дневник по этой же сессии (этот файл) — как пример по свежему шаблону.
6. *(добавлено по ходу)* Уточнить правило «когда писать» — пишем всегда, без исключений, глубина пропорциональна масштабу.
7. *(добавлено по ходу)* Перенести поведенческие правила (напоминание создать файл, живое обновление плана, актуализация индексов) в `CLAUDE.md` — это инструкции мне, не документация для людей.
8. *(добавлено по ходу)* Решить вопрос нейминга при нескольких фичах в один день и при растянутой на много дней/сессий одной фиче.
9. *(добавлено по ходу, 2026-09-17)* Закрепить формат commit-сообщений — Conventional Commits, по запросу пользователя при коммите этой же фичи.

## Сделано

- Обсудили идею как челлендж: разобрал предложенную структуру (папка `docs/features`, имя `год-месяц-день-название-ветки-или-фичи`, поля статус/цель/план/сделано/не стали/лог файлов) — указал на риски дублирования с ADR, ручного ведения лога файлов (гарантированный дрейф от кода — то же самое, что уже привело к багу в ACL-рефакторинге) и имени по ветке (ветки переименовываются, уже было в этой сессии: `fix/person-billing-kernel` → `feature/acl-refactoring-person-billing`).
- Создан [`docs/features/README.md`](README.md): разница с ADR и commit/PR, критерии «когда писать», формат имени файла (дата создания + название **фичи**, не ветки), четыре статуса (🟡/✅/⏸️/❌), отдельное поле «Обновлено» (не полагаться только на дату в имени файла), явное правило не вести «Изменённые файлы» руками — только снимок `git diff --stat`/ссылка на PR перед завершением, индекс дневников.
- Создан [`docs/features/template.md`](template.md) — Статус/Начато/Обновлено, Цель, План, Сделано, Не стали делать, Изменённые файлы, Ссылки; в разделах «Сделано»/«Не стали делать» — явное указание не пересказывать архитектурные решения, а ссылаться на ADR.
- `CLAUDE.md` — раздел переименован в «Документация решений и изменений», описывает оба места одной строкой на каждое: ADR — «почему устроено именно так», feature-лог — «что и зачем сделали в задаче», сам `CLAUDE.md` — «как устроено сейчас».
- Существующий обзорный документ перенесён пользователем из `docs/refactoring-plan.md` в `docs/features/2026-09-08-refactoring-plan.md` (до появления шаблона) — ссылки на него в `docs/adr/0001-*.md` и `docs/adr/0002-*.md` обновлены под новый путь.
- Пользователь скорректировал правило: пишем **всегда**, без исключений по размеру изменения — глубина заполнения пропорциональна масштабу. Переписал «Когда писать» в `docs/features/README.md` под это (заодно убрал противоречивую формулировку, оставшуюся от промежуточной правки на диске — заголовок обещал выборочность, текст говорил про безусловность).
- Добавлено явное правило: обязательная чистка черновика привязана к моменту смены статуса на ✅/⏸️/❌, а не «когда-нибудь потом».
- В `CLAUDE.md` добавлен раздел «Обязательный рабочий процесс для Claude Code»: напоминать про создание feature-файла при начале планирования; фиксировать план в файле сразу, а не постфактум; перечитывать `docs/adr/`/`docs/features/`-файлы заново перед правкой (пользователь может редактировать их напрямую); предлагать ADR, когда решение архитектурное; актуализировать индекс сразу при создании новой записи.
- Решили вопрос нейминга: единица группировки — **фича/задача**, не ветка (переименовывается) и не календарная сессия (одна сессия может касаться нескольких фич; одна фича может растянуться на много сессий/дней — для этого и есть поле «Обновлено»). Несколько фич в один день — просто разные слаги в имени, коллизия слага — суффикс `-2`.
- В `docs/adr/README.md` добавлено симметричное правило: индекс обновляется при каждом новом ADR как часть создания записи.
- Индекс `docs/features/README.md` дополнен строкой про этот же файл.
- При коммите этой же фичи пользователь попросил писать commit-сообщения в Conventional Commits. Первый черновик формально был валиден, но нарушал атомарность (5 разных изменений в одном `docs(process):`) и оказался многословным. По запросу расписал разбиение на 5 атомарных коммитов — пользователь предпочёл вернуться к единому коммиту, но короче. Итог зафиксирован как правило:
  - `CLAUDE.md`, раздел «Коммиты»: Conventional Commits, `type`/`scope` на английском, описание на русском, один лаконичный коммит на задачу по умолчанию, дробить только по явной просьбе.
  - персональная память (`conventional-commits-preference.md`) — та же конвенция плюс контекст «многословно» относилось к объёму, не к дроблению на коммиты.
