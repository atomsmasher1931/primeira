# Рабочий дневник изменений проекта (docs/features)

**Статус:** ✅ Готово \
**Начато:** 2026-09-16 \
**Обновлено:** 2026-09-17

## Цель

После ADR (`docs/adr/`, заведён раньше) не хватало более лёгкого места для фиксации хода конкретной задачи — не архитектурного решения, а «что делаем, зачем, что уже сделали, что решили не делать». Без этого контекст задачи жил только в чате и терялся между сессиями ассистента (в частности, ACL-рефакторинг `Person`↔`Billing` чуть не пришлось пересматривать заново на ровном месте). Цель — завести `docs/features/` как рабочий дневник фичи/ветки, с чёткой границей: где кончается ADR и начинается дневник, чтобы не дублировать одно и то же в двух местах.

## План

1. Обсудить идею (челлендж): какие риски у отдельной папки под дневники фич, сравнить с ADR и с commit/PR.
2. Сформулировать разделение ответственности: ADR — «почему архитектурно так», `docs/features` — «что и зачем в рамках задачи», commit/PR — «что именно в дифе».
3. Создать `docs/features/README.md` (правила) и `template.md` (шаблон).
4. Обновить `CLAUDE.md` — добавить ссылки на оба места с разницей в одну строку.
5. Завести первый дневник по этой же сессии (этот файл) — как пример по свежему шаблону.
6. *(добавлено по ходу)* Уточнить правило «когда писать» — пишем всегда, без исключений, глубина пропорциональна масштабу.
7. *(добавлено по ходу)* Перенести поведенческие правила (напоминание создать файл, живое обновление плана, актуализация индексов) в `CLAUDE.md` — это инструкции мне, не документация для людей.
8. *(добавлено по ходу)* Решить вопрос нейминга при нескольких фичах в один день и при растянутой на много дней/сессий одной фиче.
9. *(добавлено по ходу, 2026-09-17)* Закрепить формат commit-сообщений — Conventional Commits, по запросу пользователя при коммите этой же фичи.

## Сделано

- Обсудил предложенную структуру как челлендж: риски дублирования с ADR, ручного ведения лога файлов (тот же класс дрейфа, что уже привёл к багу в ACL-рефакторинге) и имени файла по ветке (ветки переименовываются — было в этой же сессии: `fix/person-billing-kernel` → `feature/acl-refactoring-person-billing`).
- [`docs/features/README.md`](README.md) и [`template.md`](template.md): разница с ADR и commit/PR; пишем **всегда**, глубина пропорциональна масштабу; имя файла — дата создания + название **фичи/задачи** (не ветки, не календарной сессии); четыре статуса (🟡/✅/⏸️/❌) с отдельным полем «Обновлено»; «Изменённые файлы» — не вести руками, снимок `git diff --stat` перед завершением; архитектурные решения — не пересказывать, ссылаться на ADR; индекс обновляется при каждом новом файле как часть его создания.
- Обязательная чистка черновика привязана к моменту смены статуса на ✅/⏸️/❌ (демонстрируется прямо в этом файле — см. историю правок).
- `CLAUDE.md`: раздел «Документация решений и изменений» (ADR vs feature-лог vs сам `CLAUDE.md`, одной строкой на каждый) + «Обязательный рабочий процесс для Claude Code» (напоминать открыть feature-файл при планировании, вести план вживую, перечитывать файлы перед правкой — пользователь может редактировать их напрямую, предлагать ADR, актуализировать индексы).
- Симметричное правило про индекс добавлено и в `docs/adr/README.md`.
- Договорились про Conventional Commits для commit-сообщений (первый черновик нарушал атомарность и был многословным — итог см. `CLAUDE.md`, раздел «Коммиты», и личную память `conventional-commits-preference.md`).
- Существующий обзор `/src` перенесён из `docs/refactoring-plan.md` в `docs/features/`, затем полностью расщеплён на отдельные дневники и удалён — все получившиеся файлы и обоснование каждого шага см. в индексе [`README.md`](README.md#индекс).
- По той же логике (пишем всегда, дневник заводится сразу при планировании) отдельным файлом задокументирована ещё одна задача этой сессии — конвенция для описаний Pull Request: [`2026-09-17-pr-description-conventions.md`](2026-09-17-pr-description-conventions.md).
