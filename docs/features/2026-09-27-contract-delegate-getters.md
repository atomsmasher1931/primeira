Задача: убрать из доменной сущности `Contract` методы, которые существуют только ради сборки одного события, и перенести эту сборку туда, где ей место, — в Application-слой `Billing`. Поведение системы не меняется.

## Что такое delegate-геттер и чем он плох

**Delegate-геттер** — метод сущности, который не возвращает ничего своего, а достаёт значение у связанного объекта и отдаёт наружу. В `src/Billing/Domain/Entity/Contract.php` их восемь:

```php
public function getTariffId(): string          { return $this->tariff->id; }
public function getTariffValue(): int          { return $this->tariff->value; }
public function getTariffTypeName(): string    { return $this->tariff->getTypeName(); }
public function getTariffDegreeName(): string  { return $this->tariff->getDegreeName(); }
public function getTariffStatusName(): string  { return $this->tariff->getStatusName(); }
public function getMusicianId(): string        { return $this->musician->getId(); }
public function getMusicianEmail(): string     { return $this->musician->getEmail(); }
public function getMusicianPhone(): string     { return $this->musician->getPhone(); }
```

Идея приёма — соблюсти **закон Деметры** («общайся с соседями, а не с соседями соседей»): вызывающий код пишет `$contract->getMusicianEmail()`, а не `$contract->getMusician()->getEmail()`. Проблемы:

1. **Закон Деметры соблюдён формально, а не по сути.** Вызывающий код по-прежнему знает, что у договора есть тариф с «типом, степенью, статусом» и музыкант с «почтой и телефоном». Знание о чужой структуре никуда не делось — оно переехало в публичный API `Contract`.
2. **Интерфейс сущности растёт и меняется из-за чужих причин.** Новое поле у `Tariff` или `Musician`, нужное событию, — новый метод в `Contract`. Это нарушение принципа единственной ответственности (SRP): у `Contract` появляются причины меняться, не связанные с договором.
3. **Доменная сущность обслуживает чужой сценарий.** Эти геттеры не нужны бизнес-логике договора — они нужны, чтобы собрать плоский DTO для шины сообщений. Это забота Application-слоя.
4. **Здесь они ещё и ничего не прячут.** Рядом есть `getTariff(): Tariff` и `getMusician(): Musician`, и ими пользуются (`IssueInvoicesUseCase`, обе `ContractDtoFactory`). Инкапсуляции нет — есть дублирующая плоская проекция.
5. **Протаскивают данные чужого контекста.** `musician*` — данные `Person`, отдаваемые через публичный интерфейс сущности `Billing`. Это частный случай общей проблемы, вынесенной в [`2026-09-27-person-billing-acl-level-3.md`](2026-09-27-person-billing-acl-level-3.md).

### Когда такой геттер — это нормально

Не всякий метод, заглядывающий в связанный объект, плох. Контрпример в том же контексте — `Invoice::getPayerFullName()/getPayerPhone()/getPayerEmail()`: там сущность оперирует **своим доменным понятием** «плательщик» (роль, которую музыкант играет в счёте), а `getPayerFullName()` ещё и содержит логику форматирования. Такой метод выражает язык предметной области, а не транслирует чужие поля 1-в-1. Критерий: *если имя метода — это `get<ИмяСвязи><ИмяПоляСвязи>` и тело — одна строка делегирования, это проекция, а не поведение.*

## Кто пользуется

У всех восьми методов **ровно один потребитель** — сборка события в `src/Billing/Application/UseCase/CreateContractUseCase.php` (`new ContractCreatedEvent(...)`). Больше нигде: ни в контроллерах, ни в консюмерах, ни в тестах.

## Рекомендация

Делать — правка дешёвая, локальная и без изменения поведения:

- Удалить восемь delegate-геттеров из `Contract`.
- Маппинг `Contract → ContractCreatedEvent` вынести в Application-слой `Billing`: небольшая фабрика `Billing\Application\Factory\ContractCreatedEventFactory` (или приватный метод юзкейса, если фабрика покажется избыточной для одного вызова). Внутри — `getTariff()`/`getMusician()`, то есть знание о структуре связей живёт в одном месте, в слое, который и собирает сообщения.
- **Не** делать `ContractCreatedEvent::fromContract(Contract)`: событие живёт в `Core\Ampq\Event`, и такой метод сделал бы `Core` зависимым от сущности `Billing` — разворот направления зависимостей shared kernel.
- Проверка: `vendor/bin/codecept run unit` + `functional`; вручную — `POST` создания договора и консюмер `ContractCreated` (событие должно прийти с теми же полями).

**Порядок относительно других задач**: делать раньше [ACL уровня 3](2026-09-27-person-billing-acl-level-3.md). После этой правки данные музыканта для события будут собираться в одном месте, и замена `Musician` на снимок из `Person` затронет одну фабрику, а не API сущности.

**Не расширять в этой задаче** на `Invoice::getPayer*()` — см. «Когда такой геттер — это нормально», там это оправдано.

## Нужен ли ADR

Для самой правки — **нет**. По критериям [`docs/adr/README.md`](../adr/README.md) это рефакторинг без изменения архитектурных правил: границы модулей не меняются, технология не выбирается, спорной альтернативы с весомыми последствиями нет.

ADR понадобится, **если** решим сделать из этого правило для всего проекта — например, «доменные сущности не содержат проекций под сообщения/DTO, проекции собираются в `Application/Factory`», — и хотим, чтобы новые сущности следовали ему, а не повторяли паттерн по памяти. Это выбор паттерна, где была реальная альтернатива (оставить удобные геттеры на сущности), — подходит под критерий ADR. Предлагаю решить это после правки: если паттерн найдётся ещё где-то кроме `Contract` — оформить ADR, если нет — достаточно этого файла.
