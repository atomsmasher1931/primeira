# Best practices для описаний Pull Request

**Статус:** ✅ Готово \
**Начато:** 2026-09-17 \
**Обновлено:** 2026-09-17

## Цель

Формализовать, как писать описания PR — по аналогии с тем, что уже сделано для commit-сообщений (Conventional Commits). PR-описание пишется для ревьюера, а не для истории — у него нет контекста разговора, только диф и текст. Без конвенции описания либо пусты, либо превращаются в пересказ диффа построчно.

## План

1. Дать пользователю рекомендации по best practices (структура, на кого писать, не дублировать ADR/feature-лог).
2. Спросить, где закрепить правило в проекте.
3. Закрепить в обоих местах: GitHub PR template (работает для любого контрибьютора) + короткое правило в `CLAUDE.md` (инструкция для Claude Code).

## Сделано

- `.github/pull_request_template.md` — шаблон с разделами «Что и зачем», «Что сделано», «Как проверить», «Риски / на что обратить внимание»; HTML-комментарии с подсказками, что писать в каждом разделе.
- `CLAUDE.md`, раздел «Pull Request» (рядом с «Коммиты»): писать для ревьюера, архитектурные решения — ссылкой на ADR/`docs/features`, не пересказом; заголовок PR — в формате Conventional Commits (совпадает с commit-сообщением при squash-merge).

## Не стали делать

Ничего не отклонили — оба варианта закрепления (template + CLAUDE.md) выбраны пользователем одновременно, альтернатив не осталось неиспользованными.
